# 验证与交付规范

> 每次代码修改后必须按本文件交付。**未经验证的"完成"等于没完成**。

---

## 一、Definition of Done（DoD）

一个任务真正完成的必要条件如下；只检查适用于当前任务的项目，不适用项必须能说明原因：

- [ ] 代码改完，本地编译/构建通过
- [ ] 改到的相关测试已运行、全部通过
- [ ] 新增功能有对应测试（覆盖率门槛见 `testing-standard.md`）
- [ ] 本地手动验证了**正常路径**和**至少一个边界情况**
- [ ] 改动不影响其它模块（跑一次回归测试或冒烟测试）
- [ ] 已给出**验证 / 未验证 / 风险 / 回滚**四件套
- [ ] Git 状态已说明；如用户要求提交，提交位于合适分支且未直推受保护分支
- [ ] 涉及契约的，已同步更新 `docs/contracts/`
- [ ] 涉及 DDL 的，已提供恢复策略；安全可逆时包含回滚 SQL

**不满足任一项，必须明确说明为什么 + 怎么补**。

---

## 二、验证要求

每次修改后必须尽可能验证。命令以项目真实脚本为准：

| 验证类型 | 命令模板 | 备注 |
|---|---|---|
| 编译/构建 | `ai-spec.yaml` 或项目清单中的 build 命令 | 适用时必跑 |
| 静态检查 | linter / type checker | 改到 .ts / .java / .py 时跑 |
| 单元测试 | 项目配置中的 test 命令 | 改到的模块必跑 |
| 集成测试 | 项目特定命令 | 改到 API / DB 层时跑 |
| 本地接口 | 用项目 run 命令启动 → curl / API 客户端自测 | 改到接口时必跑 |
| 前端联调 | 启动前端 dev server 对真实后端 | 全栈改动必跑 |

**禁止用以下话术替代验证**：
- "应该可以"
- "看起来没问题"
- "理论上没问题"
- "按惯例是这样的"
- "等下我验证一下"（然后没验证）

---

## 三、未验证说明（必须时）

如果某项确实无法验证，必须明确说明：

- **未验证项**：具体什么没验证
- **未验证原因**：为什么没验证（环境/数据/权限/时间）
- **可能风险**：不验证会出什么问题
- **后续验证方式**：什么时候、由谁、用什么方式补验证

---

## 四、交付报告格式

中高风险、跨模块和正式发布任务使用以下完整 13 项结构。低风险文档或单点修改可以合并“无影响”章节，但仍必须包含目标、改动、验证、未验证、风险、恢复和后续动作：

```markdown
## 本次任务交付说明

### 1. 任务目标
（一句话说清本次要解决什么）

### 2. 实际完成内容
（按要点列出，每条对应一个可验证的变更）

### 3. 修改文件清单
| 文件 | 修改内容 | 原因 | 风险等级（低/中/高） |
|---|---|---|---|
| path/to/file | 加了 X / 改了 Y | 修复 Z | 低 |

### 4. 后端影响
（接口/服务/数据/性能；无则写"无"）

### 5. 前端影响
（页面/组件/路由/状态；无则写"无"）

### 6. 数据库影响
（DDL / 数据迁移 / 索引；无则写"无"）

### 7. 权限影响
（菜单/权限码/数据范围；无则写"无"）

### 8. 外部集成影响
（第三方 API / Webhook / MQ；无则写"无"）

### 9. 验证结果
| 验证项 | 命令/方式 | 结果 |
|---|---|---|
| 编译 | 项目 build 命令 | ✅ 通过 |
| 测试 | 项目 test 命令 | ✅ 12 passed |
| 接口 | curl POST /api/xxx | ✅ 200 |

### 10. 未验证内容
（列具体项 + 原因 + 补验证方式；无则写"无"）

### 11. 风险点
（可能踩的坑、未覆盖的边界、向后兼容性等）

### 12. 回滚方案
（代码/数据库/配置/权限四类，分别说明怎么回到改前状态）

### 13. 后续建议
（下一步该做什么、技术债、改进点；无则写"无"）
```

## 五、回滚要求

任何改动必须有**恢复策略**。优先回滚；不可逆或回滚风险更高时，使用前向修复、备份恢复或兼容切换。恢复策略分四类：

### 5.1 代码回滚
- 说明涉及的 commit hash 或文件
- 给出 `git revert <hash>` 或 `git checkout <hash> -- <files>` 的具体命令

### 5.2 数据库回滚
- 可安全逆转时提供逆向迁移；逆向操作会丢数据时不得把 `DROP` 伪装成安全回滚
- 数据迁移根据数据库能力使用快照、备份系统、影子表、导出或可验证的恢复点；不能假设 `CREATE TABLE AS SELECT` 保留完整结构
- 不可逆 DDL 必须在实施前说明恢复路径、兼容窗口、备份验证和批准人

### 5.3 配置回滚
- 说明配置项名 + 默认值 + 修改前值
- 涉及环境变量的，提供 `.env.example` 的旧值

### 5.4 权限回滚
- 说明菜单 / 权限码 / 数据范围如何撤销
- 提供 SQL 或后台操作步骤

---

## 六、验收前置检查（合并 MR 前）

- [ ] 所有适用的 DoD 项已满足，或明确说明缺口、风险和补齐方式
- [ ] 无未处理的阻断风险；CRITICAL 必须关闭，HIGH 已修复或有批准的限时例外
- [ ] 分支与目标分支无冲突
- [ ] CI 全绿
- [ ] 契约变更已同步前端/调用方
- [ ] DDL 已在 staging 跑过一次
- [ ] 回滚方案已写在 MR 描述里
